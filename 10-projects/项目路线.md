# 项目路线

这个目录用于收敛项目，不做灵感清单。项目只有在能验证能力时才值得写进来。能跑 demo 不够，必须能解释它验证什么能力、会遇到哪些概念、怎样判断是否可用。

当前优先项目按从应用到基础设施排序。读者不必全做，但每条方向页至少应该落到其中一个项目或一个同等强度的替代项目。

## 项目一：本地资料整理 Agent

目标：让 [[Agent]] 在一个小型 Markdown 仓库里工作。它能按用户目标读取文件、整理摘要、指出缺口，并在需要时提出修改建议。

最小版本：

- 只允许读取指定目录。
- 工具有 `list_files`、`read_file`、`search_text`。
- 每一步工具调用写入日志。
- 输出必须引用读过的文件。
- 找不到证据时说明缺少什么。

关键实现：

- 用 [[Agent Loop]] 控制“思考、调用工具、观察结果、继续”的循环。
- 用 [[Tool Use]] 定义工具 schema 和权限边界。
- 用 [[Context Engineering]] 控制文件片段、历史步骤和当前目标。
- 用 [[Evals]] 准备固定仓库和任务样例。
- 用 [[Security]] 限制目录和敏感文件。

常见失败点：

- 模型声称读过文件，但日志里没有工具调用。
- 一次性把整个仓库塞进上下文。
- 工具可以越权读任意路径。
- 没有停止条件，循环烧成本。

验收标准：

- 10 个固定任务中，至少 8 个能引用正确文件。
- 任意一次输出都能追溯到工具日志。
- 用户取消后停止后续模型调用。
- 越权路径请求被代码拒绝，而不是靠 prompt 拒绝。

参考项目：

- [LangGraph](https://docs.langchain.com/oss/python/langgraph)：看 durable execution、streaming 和 human-in-the-loop。
- [OpenAI Agents SDK](https://platform.openai.com/docs/guides/agents-sdk/)：看 agent、handoff、tool 和 trace 的基本抽象。
- [Microsoft AutoGen](https://autogenhub.github.io/autogen/docs/Use-Cases/agent_chat/)：看多 agent 对话和工具参与的系统形态。

## 项目二：带引用的 RAG 问答系统

目标：对一组固定文档做问答，并提供能回到原文的引用。

最小版本：

- 文档集先限制为 Markdown 或网页正文。
- ingestion 保存 `source_id`、标题、段落位置和更新时间。
- 支持增量更新或全量重建索引。
- 查询结果进入 prompt 前带来源。
- 答案必须引用来源；证据不足时拒答。

关键实现：

- [[Embedding]] 生成查询和文档向量。
- [[RAG]] 处理切块、检索、重排和引用。
- [[Context Window]] 控制证据数量和输出预算。
- [[Evals]] 拆分检索命中和答案忠实度。

常见失败点：

- 只看回答是否像样，不检查引用是否支持结论。
- 文档更新后旧索引仍被使用。
- 多用户资料没有 metadata 过滤。
- 数字、版本号和代码符号只靠向量检索。

验收标准：

- 30 个问题里记录 expected source，能看到检索命中率。
- 没证据的问题能拒答，而不是编答案。
- 文档修改后能解释索引如何更新。
- 每个答案都能回到原始片段。

参考项目：

- [LlamaIndex](https://docs.llamaindex.ai/)：看 ingestion、index、query engine 和 evaluation。
- [Haystack](https://docs.haystack.deepset.ai/docs/intro)：看 pipeline 和 document store。
- [Qdrant](https://qdrant.tech/documentation/) 或 [Milvus](https://milvus.io/docs)：看向量库和 metadata filter。

## 项目三：模型调用网关

目标：封装模型 API，提供鉴权、流式输出、日志、超时、重试和成本记录。这个项目能把 [[HTTP]]、[[SSE]]、[[Streaming Response]]、[[API Auth]] 和 [[Cost]] 串起来。

最小版本：

- 前端只调用自己的后端。
- 后端保存供应商 API key。
- 支持普通响应和 SSE 流式响应。
- 记录 input tokens、output tokens、latency 和 error type。
- 对 401、429、5xx、timeout 做不同处理。

关键实现：

- 请求级 trace id。
- 用户取消后关闭上游模型流。
- 重试只用于可重试错误，并设置上限。
- API key 不进入浏览器和日志。
- 每个用户或组织有配额。

常见失败点：

- SSE 被框架或代理缓冲。
- 用户关页面后上游请求继续跑。
- 所有错误统一返回 500。
- 没有 token 记录，成本只能月底看账单。

验收标准：

- 能记录首 token 延迟和完整响应延迟。
- 断开连接后上游请求停止。
- 错误能按类型统计。
- 一次请求的成本可估算。

参考项目：

- [OpenAI Responses API](https://platform.openai.com/docs/api-reference/responses)：看托管模型接口。
- [vLLM OpenAI-compatible server](https://docs.vllm.ai/en/latest/getting_started/quickstart.html)：看自部署模型如何兼容 OpenAI API。

## 项目四：小模型训练到后训练流水线

目标：用小数据和小模型跑通从预训练、指令微调到偏好优化的基本链路。这个项目不追求训练出强模型，追求理解数据、loss、评测和成本。

最小版本：

- 用 nanoGPT 或 LitGPT 跑一个小规模训练任务。
- 保存训练配置、数据版本和 loss 曲线。
- 再用 SFT 数据做一次指令微调。
- 准备一小组人工评测样例，比较基础模型和微调模型。

关键实现：

- [[Pre-Train]]：tokenizer、数据管线、训练循环。
- [[Post-Train]]：SFT、DPO 或 GRPO 的输入格式。
- [[Evals]]：不要只看 loss，也看任务输出。
- [[Cost]]：记录 GPU 时间和失败重跑成本。

常见失败点：

- 数据太小却期待模型学到通用能力。
- 只看训练 loss，不看生成样例。
- prompt 格式和推理格式不一致。
- 没有保存数据版本，结果无法复现。

验收标准：

- 能解释一次训练从数据到 checkpoint 的流程。
- 能复现实验并得到相近 loss 曲线。
- 能说明微调提升了哪些样例，退化了哪些样例。
- 能估算单次实验的计算成本。

参考项目：

- [nanoGPT](https://github.com/karpathy/nanoGPT)：读 `model.py` 和 `train.py`。
- [LitGPT](https://github.com/Lightning-AI/litgpt)：看 pretrain、finetune、evaluate、deploy 工作流。
- [TRL](https://huggingface.co/docs/trl)：看 SFT、DPO、GRPO 等后训练方法。
