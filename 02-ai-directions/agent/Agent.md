# Agent

Agent 是这个仓库优先展开的 AI 系统方向之一。

这里采用一个朴素定义：

> Agent 是一个能围绕目标，在上下文、工具和反馈之间循环工作的系统。

它不是“套一层 ChatGPT API”，也不是自动规划一切的营销词。这个方向关注的是模型如何读取状态、调用工具、吸收反馈，并在明确边界内继续推进任务。

## 讨论范围

本目录主要讨论工程里的 Agent，而不是泛泛讨论“自主智能体”。

包括：

- coding agent：在本地代码仓库里读文件、改代码、运行命令、处理测试反馈。
- personal agent：常驻在个人环境里，接入消息、文件、日程、浏览器或本地工具。
- workflow / orchestration agent：把模型调用、工具调用、状态流转和人工介入组织成可运行流程。
- multi-agent：用多个角色、多个执行单元或多个会话协作完成任务。

这些形态差异很大，但都会碰到同一组工程问题：上下文、工具、状态、权限、日志、评测和失败恢复。

## 核心问题

Agent 的重点不在“模型能不能回答”，而在系统如何把模型放进一个可控的执行循环里。

- [[Agent Loop]]：目标、模型输出、工具调用、环境反馈和停止条件如何组成循环。
- [[Tool Use]]：模型如何选择工具，代码如何校验参数、执行工具和返回结果。
- [[Context Engineering]]：系统如何选择放进上下文的文件、消息、工具结果和中间状态。
- [[Memory]]：Hermes Agent、OpenClaw、Mem0、LangGraph 等 memory 实现入口。
- [[Skills]]：可复用能力如何被组织、声明、加载和调用。
- [[Single Agent vs Multi-Agent]]：什么时候一个 Agent 足够，什么时候需要多个执行单元协作。
- [[ReAct]]：reasoning 与 acting 交替出现的早期研究范式，以及它和今天工程实现之间的差异。

## 工程边界

真实 Agent 系统通常不会只依赖 prompt 维持边界。

权限、读写范围、工具参数、执行超时、循环上限、用户确认、日志和回滚，都需要落到代码和运行时系统里。否则系统看起来像 Agent，实际只是一个带工具调用的聊天界面。

生产系统里的 Agent 也不一定把所有内部过程隐藏起来。对开发者和运维人员来说，trace、日志、工具调用记录、上下文快照和评测结果本身就是系统的一部分。
