# Agent

Agent 是这个仓库先写的具体方向。它适合用项目带动学习，因为你很快会碰到模型、上下文、工具、工程链路和评测。

这里不把 Agent 当营销词，也不把它理解成“套一层 ChatGPT API”。先用一个朴素定义：

> Agent 是一个能够在目标、上下文、工具和反馈之间循环工作的系统。

## 这个方向怎么读

刚开始可以按这个顺序看：

- [[Agent 信息来源]]：先知道去哪里获取靠谱信息
- [[Agent 开源项目]]：再看有哪些真实项目可以研究
- [[Agent 概念]]：最后建立最小概念地图，知道每个概念之间的关系
- [[Agent Loop]]：理解最小循环
- [[Tool Use]]：理解模型如何调用外部能力
- [[Skills]]：理解可复用工作流如何进入 Agent

不要一开始就陷进框架 API 或复杂论文。先弄清楚三个问题：Agent 在解决什么问题，真实项目长什么样，哪些概念会反复出现。

## 最小理解

一个最小 Agent 通常有这些部分：

- `goal`：要完成的目标
- `context`：当前可用的信息
- `model`：负责推理、生成或决策的模型
- `tools`：模型可以调用的外部能力
- `loop`：观察、思考、行动、反馈、修正的循环
- `eval`：判断结果是否正确、稳定、可用的方法

## 为什么先写 Agent

先写 Agent，是因为它会很快碰到这些主题：

- [[LLM]]
- [[Prompting]]
- [[Context Engineering]]
- [[Tool Use]]
- [[RAG]]
- [[Evals]]
- [[Security]]

不用先把所有概念学完。先做一个很小的 Agent，再在构建过程中补缺口。

## 第一个项目

建议做一个很小的本地资料整理 Agent：

1. 输入一个本地 Markdown 目录和一个目标
2. 让模型读取少量文件
3. 让模型生成修改建议或摘要
4. 对每一步工具调用做日志
5. 用人工检查和几个固定样例做 [[Evals]]

这个项目足够小，但会碰到 Agent 最核心的东西：上下文选择、工具权限、循环次数、失败恢复和输出校验。

## 先不追求什么

一开始不需要追求复杂 multi-agent 框架、自主规划一切的通用 Agent、花哨 UI、大规模向量数据库或过早抽象框架。

先看真实项目和基本概念，再决定自己要做什么。否则很容易把 demo 包装成产品。
